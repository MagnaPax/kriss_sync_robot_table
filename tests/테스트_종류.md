# 테스트 종류

---

### 1. `if __name__ == "__main__":` (개발자용 간이 테스트)

이 방식은 **"Smoke Test"** (연기 테스트)라고 부르며, 개발자가 모듈을 개발하는 **'중간'**에 사용하는 **'비공식적이고 빠른'** 테스트입니다.

* **목적:** `pytest` 같은 복잡한 설정 없이, 해당 파일만 독립적으로 실행해서 핵심 기능이 최소한 "연기(smoke)가 나지 않고" 잘 돌아가는지 빠르게 확인할 때 씁니다.
* **현업 사용처:**
    * 모듈을 처음 만들 때, 내가 짠 로직이 맞는지 눈으로 확인할 때.
    * 다른 사람이 만든 모듈을 이해하기 위해 "이거 어떻게 쓰는 거지?" 하고 `python -m ...`으로 간단히 실행해 볼 때.
* **한계:** 자동화가 어렵고, 테스트 케이스가 많아지면 `main` 블록이 지저분해집니다.

---

### 2. `pytest` (자동화된 정식 테스트)

`pytest`는 "이 코드는 문제가 없음"을 **공식적으로 증명**하고, 지속적으로 **품질을 보증(QA)**하기 위한 **"자동화된 정식 테스트"**입니다.

* **목적:** CI/CD(지속적 통합/배포) 파이프라인에 연결되어, 코드가 변경될 때마다 **모든 기능이 여전히 정상 동작하는지** 자동으로 검증하는 것이 목적입니다.
* **TDD (테스트 주도 개발):**
    TDD는 `pytest` 같은 툴을 *사용하는* "개발 방법론"입니다. 현업에서는 TDD를 엄격하게 따르기도 하고, 기능 개발이 끝난 후 테스트 코드를 작성(Test-After)하기도 합니다. **어떤 방식이든, `pytest`는 "자동화된 테스트" 그 자체를 담당합니다.**
* **현업 사용처 (핵심):**
    1.  `tests/`안에 테스트를 위한 **별도 파일**을 만듭니다.
    2.  `main` 블록에 있던 테스트 케이스들(성공, 키 누락, 타입 오류)을 `pytest` 함수로 옮깁니다.
    3.  `pytest.mark.parametrize` 등을 사용해 수십 가지의 예외 케이스를 체계적으로 테스트합니다.
    4.  개발자가 `feat/작업내용` 브랜치를 `main` 브랜치로 PR(Pull Request)할 때, GitHub Actions나 Jenkins 같은 툴이 **자동으로 `pytest`를 실행**합니다.
    5.  테스트가 하나라도 실패하면 `main` 브랜치로 **병합(Merge)이 거부됩니다.**

---

### 💡 현업의 현실적인 흐름

1.  **(개발 중):** 개발자는 `if __name__ == "__main__":` 을 만들어 로직을 빠르게 테스트합니다.
2.  **(개발 완료):** `tests/` 안에 테스트 파일을 생성하고 `pytest` 코드를 작성하여 `KeyError`, `ValueError` 등 모든 예외 상황을 검증합니다.
3.  **(PR/Merge):** `pytest`를 실행해 모든 테스트가 통과하는 것을 확인한 후 코드를 제출합니다.

결론적으로, `main` 블록은 **개발자를 위한 "도구"**이고, `pytest`는 **팀과 프로젝트를 위한 "안전망"**입니다.
